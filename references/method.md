# 思想材料维护

## 单一来源

正文与证据只存于 [positions.json](../positions.json)。README 介绍项目，SKILL 负责使用流程，测试记录期望；它们不维护第二份观点正文。历史来源保留不可变版本链接，不依赖来源仓库继续提供当前思想内容。

每条材料包含稳定的 `id`、`title`、`content`、`source` 和两种状态。`source.kind` 为 `model-summary`、`user-statement` 或 `proposal`，分别表示既有模型摘要、可公开的本人陈述或建议草案。摘要中的引号不等于经过核验的本人逐字引文。

## 状态与证据

| 字段              | 状态                        | 必要证据                                                 |
| :---------------- | :-------------------------- | :------------------------------------------------------- |
| `personal_status` | `unconfirmed` / `confirmed` | `confirmed` 必须有 `confirmation`                        |
| `doctrine_status` | `unratified` / `ratified`   | `ratified` 必须有单独的 `ratification`，且个人状态已确认 |

证据对象必须包含 `url` 和 `locator`，或包含 `date` 和可公开的 `statement`。本地新增的确认记录只摘录必要内容，不存整段私人对话。确立教义的 `ratification` 另含 `approved_by: lailai` 和 `scope: doctrine`，记录其明确批准的具体正文与范围；不能复制个人画像的历史确认记录来充数。修改已确认正文的含义时，旧确认不自动覆盖新稿：降回未确认状态，保留旧版本与变更原因，再核对新授权。

检查脚本只能验证结构和证据字段，无法判断一项真实授权是否发生；维护者必须核对来源原文，不把检查通过当作本人认可。

确立记录另存 `content_sha256`，使用检查脚本的 `content_digest` 对该条目的 ID、标题和正文计算摘要，绑定被批准的具体版本。更改正文会使旧记录失效；只有对应新版本的批准已核实，才可更新摘要。摘要防止误沿用旧批准，不是批准本身。

## 从材料到主张

1. 先检索已有 ID，更新同一材料，避免换标题后重复收录。
2. 先确定要讨论的维度：世界观讨论现实、知识、因果等判断；人生观讨论目标、意义与生活路径；价值观讨论取舍标准、责任与正当性。三者可以关联，但不能互相代证。
3. 区分本人直接陈述、本人作品、模型摘要、第三方表达与作者推论。逐条核对说话人和上下文：提问不等于相信，引用、转述、代拟、角色扮演和待改写文本不自动属于用户；一次行为、消费或审美偏好也不等于稳定原则。
4. 频次只能帮助发现候选主题，不能单独证明立场。重复出现的倾向仍须核查语境、反例和变化；跨导出数据应按稳定消息标识去重，避免把重复副本算成多次表达。
5. 起草时分别写清主张、依据、推理、反例、适用范围、时间性和未解决的张力。区分事实判断、价值前提与策略选择，不把描述性习惯写成规范性主张。
6. 检查逻辑蕴含边界：否定一个立场不自动证明其对立面。例如，不信仰决定论不等于确认自由意志论、非决定论或某套完整因果观。
7. 没有足够材料的部分保留为空白或列成待讨论问题，不为凑齐三观、增加条目数或形成完整体系而补写信念。只把明确、可追溯且不违背隐私边界的材料作为依据。
8. 需要正式确立新主张时，展示具体文本及相对旧材料的差异，核对本人是否已明确批准这一版本；已有批准未改变时不重复询问。
9. 同意建仓、迁移或一般优化不提升思想状态。缺少批准只阻塞确立主张，不阻塞整理、批评或拟稿。
10. 内容变化同时补充对应的行为场景。对外发布、发言或传播仍按当前任务授权处理，不由确立教义自动授权。

## 大规模资料审阅

要求从大量个人资料提炼思想时，先列出来源清单、可访问范围、格式和去重方式，再分层检索候选材料。自动检索只负责定位，不负责判定作者或立场；候选项必须回看完整相关上下文和相邻消息。

### 来源链与独立性

- 优先核对可定位的本人原始陈述；本人创作的文章可作为本人作品证据，但须排除引文、代拟段落、共同编辑内容和为特定任务撰写的角色文本。
- 聊天记录的外层角色为 `user`，不代表其中每段文字都由用户原创。若消息包含粘贴的助手回答、第三方文本、待改写草稿或引用，应按内部来源分别归属。
- 还要识别容器内材料及其作者：会话续接/交接摘要、自动生成的目标包装、Skill 或提示词正文、项目规格、转录稿和工具报告，都可能被装进 `user` 消息或用户提供的文件。分别核实摘要/报告的生成来源、转录稿中的说话者，以及规格/提示词的作者和任务作用；不能仅凭所在容器认定为用户原创或一般立场。追溯不到原始事件时，标记来源未核实。
- 混合来源的长消息须按段落拆分归属。可以单独审阅用户对所贴材料的直接评论，但不得把被评审/改写的正文也算作用户立场；评论与其引用材料属于同一语境，不是两份独立证据。
- 任务规格中的要求首先限定该项目和交付物。诸如“极其重要”“高质量”“效率优先”等措辞，不能脱离任务约束直接推广为一般价值原则；长、完整或语气强烈也不提升证据等级。
- 助手生成的人格总结、记忆摘要、自动整理的画像，以及后来复制这些内容的档案，都是二手材料。它们可以帮助定位原始对话，不能单独充当本人陈述；多份材料重复同一摘要也不构成独立复现。
- 对重要或有争议的摘要，追到最早可得的一手来源，并核实完整上下文。若追不到，明确标为“仅见历史摘要/来源未核实”，不得悄悄改写成用户原话或已证实立场。
- 用户确认过某个摘要时，只能确认其明确批准的具体命题和范围；不能顺带确认同段其他推论、扩大后的表述或后来拼接的内容。确认记录应能对应到获准的具体版本。

明确区分“已检索”“已抽样复核”和“逐条人工阅读”，如实报告覆盖范围、排除项、解析失败和剩余不确定性。不能把全量文件扫描、关键词命中数或模型摘要描述成逐条阅读，也不能因资料量大就推断结论更可靠。

## 论证与反方审查

个人立场可以作为待讨论材料，不因此自动成为 laiism 教义。若要发展为论证，应至少检查：

- 关键概念是否稳定，主张的对象与范围是否明确；
- 事实前提是否有独立依据，推理是否从前提有效到达结论；
- 是否存在强反例、反向案例或与其他已确认立场的张力；
- 主张是描述、预测、建议还是道德规范，是否混用了这些层次；
- 修订后保留了哪些核心承诺，又改变或放弃了哪些内容。

呈现反对意见时优先写最强版本，不为维护 laiism 或迎合本人而弱化批评。找不到可靠答案时，明确保留争议，不伪造闭合体系。

## 私人材料的抽象边界

用户允许参考私人材料，不等于允许公开原文或可识别细节。只保留完成思想整理所需的抽象命题；不写入姓名、原句、具体事件、关系经过、账号、文件路径或能反向识别当事人的背景。不得把聊天中被引用、转述、代拟或由他人表达的观点归给用户，也不得仅凭话题出现频率推断为信仰。

仅从私人材料归纳、尚未由用户逐条核对的内容，必须使用 `source.kind: proposal`、`personal_status: unconfirmed` 与 `doctrine_status: unratified`。若无法在不暴露隐私的前提下表达，宁可不收录。来源字段只说明这是待核对提案，不复制私人记录的位置或内容。

## 本次迁移的解释边界

保留历史已确认的个人立场，不等于将其确立为 laiism 教义。旧观察表与后续确认日志冲突时，以能定位到具体条目的后续确认记录为准，不能整批提升同一观察栏中的其他内容。

利益与道德判断只迁移后来确认的人格摘要；旧候选条目中的更激进推断没有随之取得确认，不重新补入。迁移时的状态只是历史记录；后续本人澄清后的当前正文、依据与状态以 `positions.json` 为准。

日常行为、说话方式、代码习惯和排版规则不因与某个思想有关就迁入这里。跨项目可以按 ID 引用，不能复制正文后各自修改。
